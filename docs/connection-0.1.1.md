# 0.1.1 连接排查记录

所有时间为中国标准时间（UTC+8），日期 2026-11-11。

## 已取得证据
- 查香港 Traefik 00:00–00:03 窗口：疑似手机的请求源（与 box 不同）在 00:01:21–00:01:35 的 `/v1/me`、`/v1/me/privacy`、`/v1/conversations`、`/v1/folders` 均为 200；`/v1/ws` 已路由至轻聊容器。两个 WS 日志记录时长约 3.0s 和 7.4s，状态字段为 **0**。Traefik 对 hijack 升级记录的 0 不能当成 HTTP 失败，也不能当成 101。
- 后端容器该窗口没有逐请求应用日志，只有启动日志，因此不能从旧日志确认手机收到了哪一条 WS 帧。
- 原版 0.1.0 的 Dart ChatEngine 直接连接香港 HTTPS/WSS：登录、REST、hello、sync.resume 全流程在约 3s 内完成，online=true。
- 用户后续真机截图已显示“已连接”，00:04–00:05 已发送图片和文本。因此“永久连不上/服务器不支持 WS”并不成立，不能虚构一个确定的手机网络根因。
- URL 规范化、Bearer header、hello/resume 协议与服务器一致；release 主 manifest 有 INTERNET，公网 HTTPS 不受 cleartext 禁令影响；JSON 为 Dart map，无 Java 反射序列化，因此没有发现 R8 破坏模型的证据。

## 代码确认的恢复缺口
1. `channel.ready` 只代表 WS 升级完成；原代码未给 hello/resume 设置期限，传输半开时会一直显示未连接，而且不会主动重建。
2. `resume()` 在 online/connecting 已置位时直接被 connect() 的守卫跳过；Android 睡眠或网络切换留下的死连接不会立即刷新。
3. REST 仅给响应头等待设置超时，响应体读取可以无限等；心跳发送后没有应用层失活检测。
4. 非 ApiFailure 原因被统一成“自动重连”，缺少可供真机回报的连接阶段。

## 0.1.1 修复
- hello/resume 应用握手 12s 超时，失败自动指数退避重连；45s 没收到帧时由周期检查识别（检查周期 20s，实际最迟约 60s）。
- 回前台/Android 默认网络变化强制清理旧连接并立即连接；旧 generation 帧与错误不会污染新连接。
- HTTP 响应体也有期限；设置页显示 connectionStage 和不含敏感值的最近异常类型。
- 标题左侧 1s 去抖、动态省略点、220ms 垂直交叉淡变，无连接横幅；聊天页副标题同样处理。

确定修复的是以上可重现的恢复缺口，不声称已复现或唯一解释用户当时的弱网等待。仍需 Xiaomi 真机覆盖首次连接、切网和回前台。

## 媒体回复核验
只检查真实消息元数据（不记录正文或令牌）：两条文本的 reply_to 均为有效字符串，原消息 kind=image 且 text 长度为 0。空引用不是伪回复，而是 UI 直接取 parent.text，遇到无 caption 图片得到空字符串。已改为发送者 + 图片缩略图 + “图片”/caption；其他媒体使用相应摘要，原消息缺失时分页补取。
